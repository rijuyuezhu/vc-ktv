# 4 Mbps 播放码率实验（2026-11-01）

## 背景与开关

当独立电视播放器通过带宽约 4 Mbps 的 VPS 反向代理读取 MP4 时，单靠提前缓冲无法保证高码率歌曲全程不断流。应用现有的 `FileResponse` 流式播放仍走 VPS，不能假定客户端直接连接 Spark-WSL。实测公网入口在本次实验期间返回 502，因为生产服务处于停止状态；下面的样本来自隔离环境，**不是生产路径的实测卡顿率**。

新增仅服务端启用的 `VC_KTV_VIDEO_MAXRATE_KBPS` 环境变量，默认 `0`（不限码率、与既有编码完全相同）。设置 `3000` 时，字幕烧录使用 H.264 CRF 23 加 `-maxrate 3000k -bufsize 3000k`（一秒 VBV）；若额外开启 30 MB 二次压缩，该路径也不会超过视频限码率。保留原视频音轨，分辨率不变，视频仍为 MP4，可正常下载。只有下一次字幕制作会读取新环境值；历史成片和原片不重编码。失败回退编码同样保留限速设置。

建议先只在独立测试服务里启用此选项。**合并 PR 不自动修改生产服务的环境变量或编码默认值。**

## 三首真实歌曲全曲重编码

在 Spark-WSL 使用历史已存档的原视频和相同的 ASS，隔离重跑视频编码；不使用任何生产队列、模型服务或活动数据库写入。`ffprobe` 根据整个 MP4 的文件大小和时长计算平均 Mbps，并根据音视频 packet size 计算最坏 10 秒窗口吞吐；SSIM 是新限速成片相对历史未限速成片的逐帧比较，并非与未烧录字幕的源视频比较。音频用 FFmpeg `-map 0:a -c:a copy -f md5` 验证一致。

| 歌曲 | 原片平均 | 未限速成片平均 / 10s 峰值 | 3 Mbps 视频上限成片平均 / 10s 峰值 | 新旧成片 SSIM |
| --- | ---: | ---: | ---: | ---: |
| Monologue | 1.538 | 4.554 / 7.022 | **2.912 / 3.291** | 0.9770 |
| 此刻 Memories | 1.467 | 3.531 / 6.669 | **2.783 / 3.218** | 0.9868 |
| 上山岗 | 1.129 | 3.668 / 6.207 | **2.616 / 3.050** | 0.9806 |

以上峰值为 Mbps，含音频（视频上限为 3 Mbps，不代表整个 MP4 严格 3 Mbps）；音频 MD5 在三首均一致。三首都低于单路 4 Mbps 的平均与 10 秒窗口预算，仍要保留连接拥塞、实际网络波动及 TCP/HTTP 额外开销的余量。SSIM 仅用于描述与未限速编码的像素差异；是否肉眼可接受应在实际投屏设备上试听查看。

全量原始记录、完整编码后的独立 MP4、FFmpeg stderr、40 秒小样本及编码脚本保存在：

`~/.local/share/vc-ktv/pipeline/benchmarks/20261101-4mbps-vbv/`

具体指标：`full-results.json`、`results.json`。不把版权音视频或真实会话数据库放入 Git。

## 浏览器与适用范围

测试环境采用独立的 FastAPI 视频响应，按 32 KiB 分块、约 500,000 B/s 发送，支持浏览器 Range 请求，以模拟**单路** 4 Mbps 瓶颈。视频来自上面独立生成的真实文件，不需要修改现有服务或 TT。浏览器实际启动延迟、等待事件、缓冲区和进度以单独的浏览器测试为准。注意模拟链路不等价于 TT 实际出口、CDN、Nginx 缓冲和并发客户端，仍需在有条件时做真实链路验收。

### HP Chromium A/B 实测（模拟 4 Mbps）

同一首 Monologue，从浏览器正常启动播放 55 秒，两个版本都没有播放中途等待；未限速版播放进度约 54.19 秒，已缓冲至 56.51 秒；3 Mbps 版进度约 54.21 秒，已缓冲至 73.64 秒。两个版本初次等待约 0.7 秒。

针对 `ffprobe` 显示的高峰（约 197–214 秒），另外在浏览器里 seek 到 190 秒，观察接下来 40 秒的真实媒体事件：

| 从 190 秒处 seek 后 40 秒 | 未限速 | 3 Mbps 上限 |
| --- | ---: | ---: |
| 播放中途 `waiting` 事件数（不含初次 seek） | **4** | **0** |
| 播放中途等待累计（由 waiting→playing 事件计算） | 约 11.6 秒 | 0 秒 |
| 40 秒墙钟结束时播放位置 | 210.09 秒 | **224.07 秒** |
| 首次 seek 等待 | 约 8.2 秒 | 约 5.9 秒 |

这证明在本次受控链路与所选高峰片段里，限码率成片可以消除可复现的播放中途卡顿。但不能据此承诺所有视频或实际 TT 出口绝不卡顿。原始浏览器事件与脚本存放在同目录的 `vcktv107_browser_results.json`、`vcktv107_peak_results.json` 及对应 Python 文件。

同一出口如果同时播放多路视频或有人下载成片，各请求单独限码率不能保证**合计**低于 4 Mbps；应避免多用户并发透过该出口下载大型文件，或额外在反向代理层实施整体带宽策略。暂不引入复杂的多清晰度/双成片体系；若需要极致画质下载，可保留原始媒体供下载并在后续验证双版本需求。
