# VC KTV 与 AutoASSrenderer4karaOK：产品取舍与功能边界

记录日期：2026-10-29。比较基于：

- VC KTV：`main` 中已合并的上游处理链路与多人点歌功能（#26、#27、#28、#29）
- 上游：[Volta233/AutoASSrenderer4karaOK](https://github.com/Volta233/AutoASSrenderer4karaOK)，固定提交 `39cedb317c9e11add83e9a72c31368cabd8416d4`（见 [UPSTREAM.json](../third_party/autoassrenderer/UPSTREAM.json)）

## 定位

**VC KTV 是多人活动中的点歌、排队与自动播放系统。** 客人输入 BV 号，选择对应的歌词，系统自动准备字幕视频并在 TV 页面连播。成功标准是尽量少操作，同时在多人环境下保持队列公平、场次隔离、播放不中断。

**上游是面向创作者的单首歌曲字幕视频制作工具。** 用户导入媒体、确认歌词，运行模型，检查或修正时间轴及字幕样式，保存项目并导出可反复修改的成品。两边关注的交互过程不同，不应照搬彼此的界面。

## 两边相同或已复用的能力

| 功能 | 本项目决定 |
| --- | --- |
| Kim Mel-Band Roformer 分离人声（仅推理） | 复用上游 |
| 双遍 Qwen3-ASR 片段识别、TIFA 歌词定位 | 复用上游 |
| 小于 90 秒的 TIFA 安全分块、局部重试、接缝修复 | 复用上游 |
| 原文/识别文本区分、逐字时间、估算标记 | 复用上游 |
| ASS 卡拉 OK 双行高亮和 MP4，保留输入原声 | 复用上游 |
| 本机 CUDA 模型运行、不调用在线 LLM | 一致 |

移植代码在 `ktv_app/`，VC KTV 的薄接入层是 `vc_ktv/upstream_pipeline.py` 和 `autoprep.py`；上游版本和资源来源可追溯。算法准确性不能从通过自动化测试推断为整首歌已人工验证。

## VC KTV 独有、应保留的能力

| 范围 | 不对齐上游的理由 |
| --- | --- |
| BV 视频解析、分 P、媒体下载和备用公开接口 | 自动点歌需要，不应强迫客人上传文件 |
| KTV 场次、加入码、用户身份、签名选词 | 多人共享系统必须明确点歌者和场次归属 |
| 公平轮播 / FCFS、已唱次数与状态队列 | 上游没有多人演唱调度的产品需求 |
| 独立 TV 页面、自动连播、唱完和跳过 | KTV 的核心交互，不属于视频制作工具 |
| 自动准备、字幕门槛、后台失败重试和隔离归档 | 不应阻断其他正在等待播放的歌曲 |
| VCPedia 来源的虚拟歌手歌词 | 继续保留本项目特别有用的来源 |
| Spark-WSL Linux ARM64 运行与生产服务 | 不复制上游 Windows x64 的安装/GUI 体系 |

## 上游有而 VC KTV 没有的能力及决定

| 上游功能 | 我们的处理方式 | 对应工作 |
| --- | --- | --- |
| 网易云音乐歌词、UtaTen、J-Lyric、繁简/日文歌名检索 | **采纳**：保留 VCPedia、LRCLIB，新增有限且来源明确的检索；只把候选交给点歌者 | [#36](https://github.com/rijuyuezhu/vc-ktv/issues/36) |
| 丰富的检索来源与曲名/歌手/时长证据 | **部分采纳**：沿用上游的名称变体和固定来源正文解析，展示来源和歌手，不把排名解释为已验证演唱版本 | #36 |
| 字幕字体、大小、颜色和位置调节 | **已实现**：管理员按本场切换三种预设（经典双行、大屏高对比、简洁单行）；不暴露完整参数编辑器 | [#37](https://github.com/rijuyuezhu/vc-ktv/issues/37) |
| 交互时间轴编辑、逐字修正、撤销与波形预览 | **暂不采纳**：不要求每位点歌者手工校对；如有实际需要，再考虑管理员高级入口 | 以后按需求另开 Issue |
| 单曲工程管理、版本历史和反复导出 | **暂不采纳**：以 KTV 的场次、原片和制作尝试归档为主 | 暂无 |
| 音频 + 静态背景图生成视频 | **暂不采纳**：主要输入是 BV 视频；管理员已有手工媒体入口 | 暂无 |
| 上游的完整 GUI、Windows 安装、下载器与项目数据库 | **不复制**：与当前多用户服务重叠、增加维护负担 | 暂无 |
| 全量人工诊断指标和模型调试面板 | **必要信息留档**：日志、来源和补齐信息保留在制作目录；不把技术中间过程塞给普通用户 | 暂无 |

## 本轮已经决定的交互规则

1. **歌词始终由点歌者本人选择。** 搜索建议只说明“来自哪里、歌名/歌手是什么、原文是什么”，不自动选择第一名，不把 ASR 输出或翻译当成最终歌词。选择仍使用与场次、歌曲、来源、歌词摘要绑定的有时效签名；其他用户不能替点歌者选。
2. **检索失败不应损坏已找到的候选。** VCPedia + LRCLIB 保留；当候选不足或来源单一时追加网易云原文 LRC、UtaTen 和 J-Lyric 的真实歌词正文以及有限的中日文字形变体。六个候选优先覆盖不同来源。来源网页不做登录绕过；搜索摘要不是歌词正文；丢弃译文/罗马音伴随轨和注音。
3. **字幕默认全自动。** 不要求用户听写、纠错或学习时间轴。出现错位可重试；管理员手工导入 TextGrid 功能继续保留，但不作为日常必经步骤。
4. **字幕样式留给管理员。** #37 每场可选择“经典双行/大屏高对比/简洁单行”，由上游 `Style` 渲染。任务被领取时快照样式，途中修改设置不改变当前任务；已完成歌曲只允许管理员在尚未播放时主动“按新风格重制”，失败继续保留旧成片。场次间配置完全隔离。
5. **不在本轮开展代码 KISS 重构。** [#32](https://github.com/rijuyuezhu/vc-ktv/issues/32) 保持独立、暂缓执行，不为了统一两边的工程架构而重写上游算法。

## 实施状态和验证边界

- #36：此文与歌词来源功能在同一 feature PR 中提交；合并后 GitHub 主线具备新来源，**不表示已上线生产**。在 Spark-WSL 独立联网验证“千本桜”时，约 9.2 秒内返回 LRCLIB 4 个、网易云音乐 1 个、UtaTen 1 个候选；J-Lyric 已经通过离线正文与固定域名回退测试，但不宣称这次实际联网命中。
- #37：本轮实现三种管理员预设，并复用上游样式和 ASS/FFmpeg 输出，不引入新的字幕引擎。默认经典双行；在预设实现合并进入 `main` 后生效，生产部署另行批准。
- #32：暂不开展 KISS/cold refactor。
- 本文是架构与产品取舍记录，不代替真实日语歌曲和歌词网站在线可用性验证。网站可能因地区、网络或协议变化失败，下载/使用内容时仍需遵守原作者权利。
