# 自动准备与字幕

## 当前流程

1. 用户提交 BV 号，系统解析公开可用的视频信息、歌曲时长和分 P。
2. 后台下载原片，默认最高 720p，可改 480p。下载失败有限次重试，其他歌曲不受影响。
3. 点歌者从多个来源选择歌词；不会自动替用户决定翻唱版本。
4. 默认 `quality`：提取音频，Kim 分离人声，双遍 Qwen3-ASR 定位演唱内容；对**每个非空 ASR 窗口**执行 TIFA 原生词定时，可信切点用于尽量优化分块。**没有任何 TIFA 分块时长硬上限**：无法安全切开就继续尝试长块，而不是仅凭秒数终止。Kim 失败改原音轨，ASR/TIFA/切片/时间轴失败降级为保留完整原歌词的估计字幕，失败原因和估算标签进入报告。实际烧录失败尝试低资源参数重试；只在原视频本身不可用或烧录最终失败时结束字幕制作。模型阶段无固定执行时长上限。PR #62 的拟声词读音映射继续保留，显示原歌词。
5. 原视频音轨不变；烧录完成后才替换待播原片，不会中途替换正在播放的视频。默认只做首遍 H.264 编码；勾选「二次压缩」才尝试将超过 30 MB 的首遍成片压到约 30 MB，失败时保留首遍可播放成片。

未选歌词、下载失败或字幕失败时保留已取得的原片。默认只有带字幕或管理员手工上传的成片可播放，管理员可允许无字幕播放，或只对某首歌跳过字幕。生成失败可重试字幕，不必重新下载原片。

## 管理员设置何时生效

| 设置 | 生效时机 |
| --- | --- |
| 公平轮播 / 先来先唱 | 下一次队列计算 |
| 允许播放无字幕 | 下一次播放判定 |
| 720p / 480p | 下一首开始下载时 |
| 字幕风格 / 二次压缩 | 下一首开始字幕制作时 |
| 暂停点歌 | 保存后立即禁止新点歌 |

本场最多同时有 1000 首未结束歌曲（等待、制作中、可播放及正在播放）。暂停点歌或满额时，普通用户无法新增歌曲；现有登录、选词、取消、下载、制作和播放不受影响。管理员可在暂停时安排重唱，但满额时同样不能新增。保存后无需重启；已经领取的任务仍使用旧配置。新场次恢复默认设置。

## 队列与权限

普通用户可以取消自己还未播放的歌、下载本场已经完成的媒体和查看已唱歌单。管理员可以取消待播歌曲、重新制作字幕、上传成片、安排已唱歌曲优先重唱。手动投屏模式需管理员领取并确认唱完或跳过，视频下载本身不改变演唱计数。

公平队列仅按**已唱首数 + 虚拟调度偏移**排队，不按时长排序。只有已可播放且参与队列的用户计入比较：如果有人落后超过两首，领取下一首普通歌曲时把他的虚拟进度提升到当前最高进度减两首，保证最多两首补偿，之后继续多人轮流。注册或刷新页面不产生补偿，补偿在领取普通歌曲时持久化，重新登录或服务重启不会重置。未开始的取消不计轮次；普通歌曲被领取后跳过只消耗虚拟轮次，不计真实演唱；管理员指定下一首或优先重唱属于**假想管理员轮次**，不计任何用户的真实演唱首数、时长或虚拟轮次，也不改变普通队列最近演唱者。先来先唱按点歌顺序播放，管理员指定下一首仍最高优先级。

独立电视播放页在当前歌曲接近结束、当前视频缓冲充足时，使用第二个原生 video 元素预加载队列的下一首候选。预览只读、不领取歌曲；正式切歌仍先由服务端确定下一首，并核对歌曲 ID 和媒体文件版本，不匹配就正常加载。浏览器决定实际预缓冲大小，预加载失败不影响当前播放；手动投屏不预加载。

## 故障排查

管理员点击歌曲详情可查看准备阶段和**真实耗时**。完整字幕尝试的日志保存在歌曲媒体目录中的 `attempt.json` 和对应 `pipeline/` 下；只报告实际执行过的阶段，旧歌不会补造耗时。自动字幕失败时先查尝试日志，再判断下载、分离、对齐或 FFmpeg 哪一步出错。模型权重、音频源和运行时版本不会被写入 Git。

更多代码和运行信息见 [开发文档](DEVELOPMENT.md)、[模型环境](SPARK_WSL_PIPELINE.md) 及 [对齐说明](ALIGNMENT.md)。

## 模型路径

Kim、Qwen 和 TIFA 的权重、源码及运行时统一存放在 `~/.local/share/vc-ktv/pipeline/`，不引用仓库下的 `.runtime` 或早期的 `vc-ktv-pipeline-staging`。环境与权重由独立安装命令准备。生产现有 systemd 配置若显式设置 `VC_KTV_PIPELINE_MODE=global-kim`，合并 PR 后仍需另行审核并切换为 `quality`，不能在开发时重启生产。

## 并行处理

`VC_KTV_PREP_WORKERS` 是**同时准备的最多歌曲数**，不是凑齐该数量才能执行的批大小。配置为 `4` 时，有 1、2、3 首就分别立即处理 1、2、3 首；有至少 4 首则最多同时处理 4 首，任意 worker 完成后即可领取下一首。队列为空的 worker 约每秒轮询一次，没有批次等待门槛。默认 `1` 保留现有部署兼容；切换到多 worker 时显式配置为 `4`。

各 worker 使用独立的音视频文件和推理进程，数据库任务领取及完成时状态更新受同一场次锁保护。`active_claims` 记录所有正在处理的任务，即使其中一些已经结束，也必须等最后一首完成才允许关闭场次。每首歌始终执行完整 Kim、双遍 Qwen3-ASR、全部非空 ASR 窗口 TIFA、可信歌词大块与接缝修复，以及视频刻录，不跳过任何阶段。

建议在 Spark-WSL 上使用：

```sh
VC_KTV_PREP_WORKERS=4
VC_KTV_KIM_SINGLE_FLIGHT=1
```

第二个变量让 Kim CUDA 推理同一时间仅运行一个实例（位于正式 pipeline 数据目录的跨进程锁）；其它歌曲的 Qwen、TIFA、下载和 FFmpeg 仍可并行。单首没有其它任务争用时通常比多首并行更快，但并非时延保证。2026-10-30 六首历史歌曲完整质量流水线的实测：串行 2129.646 秒，3 worker 861.527 秒，**4 worker 756.814 秒（2.81× 串行吞吐）**，6 worker 829.072 秒。三种并发方案全部六首 MP4 SHA-256、Qwen 窗口及 TIFA/字幕时间轴与串行基线一致。原始记录：`~/.local/share/vc-ktv/pipeline/benchmarks/20261030-six-song-throughput/REPORT.md`。该实验不修改生产配置；生产升级与模式切换仍需单独审批。
