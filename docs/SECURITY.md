# 安全与部署边界

VC KTV v0.5.0 是个人/小范围可信网络原型，并非公开可访问的多租户服务。

## 已有防护

- 管理员会话和点歌者会话由签名、HttpOnly、SameSite=Strict Cookie 识别；操作有来源校验。
- 歌词候选带有短期签名，关联歌曲、来源和歌词文本摘要；其他点歌者不能替换已点歌曲的歌词；存在有限搜索限流。
- 视频使用签名媒体 URL；签名电视控制链接有时效，属于必须保密的控制凭据。
- 后台只通过公开 B 站接口获取媒体，不接受任意用户定义的源 URL；CDN 下载使用 HTTPS 和域名白名单，限制最大 512 MiB。
- 生产密码、数据库、权重和视频不保存在 Git。应用默认监听 127.0.0.1，显式配置才会绑定其他接口。

## 当前不足（公网开放之前必须评估/补齐）

- 普通点歌需要六位加入码和本场账号，并限制 1000 首未结束歌曲，可由管理员即时暂停新点歌；这不等于完整的请求配额或计算资源隔离。
- 应在可信代理层提供 HTTPS；当前默认站点只是 HTTP，不能在不可信网络传播管理 Cookie 或电视链接。
- 管理/电视控制不是强多管理员租约模型。多个同时连接的控制页面及断线重连的互斥行为还需要增强。
- B 站接口、媒体许可与可用性随时可能变化；不要绕过加密、付费墙或账号权限。
- TIFA 和 FFmpeg 处理第三方音视频素材，建议部署在资源受限的可信环境，保证磁盘、CPU 和内存上限。
- 完整的 Android 乐播 SDK/包厢接收机验证仍未完成。

不要在 issue、PR、CI 日志中分享 ~/.config/vc-ktv、~/.local/share/vc-ktv 目录内容、浏览器的 cookie 或签名媒体/电视 URL。发现安全问题时先在私有仓库内报告。

## TT 反向代理登录限流

后续将 TT 通过反向代理接到 Spark 时，可在 Spark 的 VCKTV 服务环境设置 `VC_KTV_TRUSTED_PROXY_IPS`，值为 **TT 连接 Spark 时实际使用的源 IP**（多个 IP 逗号分隔），不是用户的公网 IP。服务只在 TCP 对端匹配此列表时读取 `X-Real-IP`，否则沿用直连 IP。反向代理**必须覆盖**该头，而不是透传客户端提供的值，例如 Nginx 使用 `proxy_set_header X-Real-IP $remote_addr;`。未配置时不会信任客户端自行传入的转发 IP；不支持通配符，不能设为整个公网。账号登录限流还按用户名独立统计，以减少同一个出口的无关账号互相误锁。

代理本身的 HTTPS、请求体限制和日志隐私需要部署 TT 时单独配置，本轮不更改。不得将签名电视链接的查询参数记录到可公开访问的日志。
