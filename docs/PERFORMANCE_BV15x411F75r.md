# 《笼中少女》字幕制作性能分析

2026 年 10 月 29 日，Spark-WSL。对应 [Issue #42](https://github.com/rijuyuezhu/vc-ktv/issues/42)。

## 结论

当前 237.85 秒的完整歌曲，第一次**成功完成**字幕视频制作耗时约 **426 秒（7 分 6 秒）**，制作速度约为视频时长的 1.79 倍。瓶颈不是下载或视频编码，而是 Qwen3-ASR 和多轮 TIFA 对齐：376 秒，占制作时间约 88%。模型使用 CUDA，但 TIFA 阶段的大量时间消耗在 CPU 相关处理与串行批次上；仍需进一步基于代码和对照实验区分 G2P、数据装载与推理本身，不能据此断言 GPU 完全没有工作。

尤其值得注意，歌词不是只做一次 TIFA：

1. Kim 从原片分离人声，仅用于识别。
2. Qwen3-ASR 对短窗口做**错开双遍**识别，本曲共 41 个窗口。
3. TIFA 为这 41 个识别窗口取得原生字词时间。
4. 根据可信切点把原歌词分为 **6 个大块**，再逐块运行 TIFA 对齐原歌词，含必要的局部恢复。
5. 补齐、生成 ASS 与 LRC、FFmpeg 烧录视频；成品保留原音轨。

因此，简单把 Qwen 的 70 秒称为“整个对齐时间”会严重低估成本。优化前必须保证原词对齐、重复副歌归属和模型来源标记仍可靠。

## 完整测试结果

| 阶段 | 第一轮成功完成（秒） | 第二轮复测（秒） |
| --- | ---: | ---: |
| 提取音频 | 0.363 | 0.366 |
| Kim 人声分离（含环境检查） | 41.162 | 54.095 |
| Qwen/TIFA 与六块原歌词对齐 | 376.439 | 362.350 |
| 完成时间轴 | 0.033 | 0.029 |
| 生成 ASS、LRC | 0.009 | 0.009 |
| FFmpeg 烧录 MP4 | 7.897 | 7.547 |
| **端到端制作总计** | **426.227** | **424.703** |

对齐阶段内部记录如下：

- Qwen3-ASR 双遍：41 窗口，分别 `asr_elapsed=70.429` 秒和 `68.509` 秒；第一轮 Qwen 模型报告的 PyTorch 显存峰值约 4.376 GiB。
- 第一轮 TIFA（识别窗口定时）：分别 `tifa_timing_elapsed=166.478` 秒和 `164.273` 秒，两轮均无时间戳窗口失败。
- 组合剩余分别约 **139.5 秒**、**129.6 秒**：六块原歌词 TIFA 对齐、切点规划、恢复和进程开销（通过差值计算，不能直接视为纯推理耗时）。
- 两轮都在第五、六块之间触发相同的接缝合并修复 `join_4_5`，这是有额外开销但保护对齐质量的真实路径，不应为加速而无条件关闭。

每 5 秒采样，GPU 显存峰值两轮均约 **5,218 MiB**，子进程 RSS 峰值分别约 **3,012 MiB** 和 **2,979 MiB**。第一轮 `ps` 进程树 `%CPU` 加总最大值约 **840%**（是进程生命周期平均占用指标，而非严格的瞬时硬件利用率）。这些是采样最大值，不保证捕获瞬态峰值，也不能与 PyTorch 内部显存计数直接等同。

两轮均成功生成 MP4：**19 行有字幕、382 个有时间戳的单位、0 个估算单位、0 行漏匹配、0 个 warnings**。两轮输出视频大小同为 14,172,132 字节。输入和两份输出 AAC 流的 MD5 均为 `a707f005f002a361ac306f475fd285ff`。

## 第二轮运行与缓存解释

第二轮使用相同下载视频、相同歌词、相同模型与新的空工作目录，数据在 `second/metrics.json`。**端到端只快了 1.524 秒（0.36%）**，整体并没有明显变化；Kim 反而慢了 12.933 秒，被 Qwen/TIFA 减少的 14.089 秒基本抵消。因此不能把第二轮称为有显著收益的“热缓存优化”。注意每次 CLI 运行都会重新启动独立的 Kim、Qwen 和 TIFA 子进程；“第二轮”体现的是**文件缓存和进程初始化的变化**，不是常驻模型的热推理。

前两次尝试因为 profiler 的 worktree 运行路径没有正确传递到现有 TIFA virtualenv，停在 TIFA 预检，分别记录在 `cold/` 与 `cold-retry/`。这些**profiler 配置错误不是模型本身的失败**；其两次 Kim 时间 58.562 秒和 41.112 秒只能作为初始缓存差异的观察，不能混入完整端到端统计。成功的第一轮名为 `cold-fixed`，但因模型文件已经经过失败尝试预热，不能严格称为真正“冷文件缓存”。

## 复现及原始数据

本地命令（只在 Spark-WSL 执行，要求原始文件与模型资产已准备好，勿在生产服务运行时抢占 GPU）：

```bash
cd /home/user/Code/vc-ktv
# 此脚本随 #42 并入 main 后可在普通检出执行
root="$HOME/.local/share/vc-ktv-pipeline-staging/profiles/bv15x411f75r-20261029"
uv run --locked python -m scripts.profile_spark_pipeline \
  --source "$root/download/source.mp4" \
  --lyrics "$root/confirmed_lyrics.txt" \
  --tifa-root "$HOME/Code/vc-ktv" \
  --out "$root" --name second
```

示例中的 `--name second` 指向已经存在的目录；为保护原始实验数据，脚本默认拒绝覆盖。若需复测，可使用**新的** `--out` 目录，并以同样输入重新运行。具体模型权重/环境见 `docs/SPARK_WSL_PIPELINE.md`。

原始数据包括：`download-metrics.json`、`input-manifest.json`、`cold-fixed/metrics.json`、`second/metrics.json`、`*.log`、各自的模型工作目录、ASR `recognition.json`、TIFA batch progress 和字幕 `export_report.json`。机器本地保留原媒体及歌词，不将版权媒体提交到 Git 仓库。

## 低风险优化方向

**首先：对齐的重复计算。** 核查 41 个 ASR 窗口的 TIFA 定时是否都需要执行，双遍时是否有可复用的局部时间信息，以及六块原歌词的 TIFA 是否可以通过更便宜但同样可信的证据约束范围。必须做质量回归，不要以速度换掉时间戳来源和音频对齐质量。

**其次：模型生命周期。** 当前单曲每次重启模型 worker，并且串行执行多段工作。可以尝试复用 worker/批处理，但应先测冷/热加载、资源峰值和长时间常驻的代价；不可默认保留 4+ GiB 模型就一定更好。

**最后：队列体验。** 用户不需要等字幕制作完成才能提交下一首歌，管理员现在可以查看主要阶段，必要时对**单首歌**选择原片入队，避免一首耗时的字幕任务卡住整场队列。此操作不会瞬间杀掉已运行的 GPU 任务。

目前只是性能分析，**没有修改原有 Kim、Qwen、TIFA 算法**。后续优化应独立开 Issue 并保持同源输入与同样准确性要求。

后续针对重复 TIFA 工作与串行开销的专项优化，单独跟踪在 [#45](https://github.com/rijuyuezhu/vc-ktv/issues/45)；不属于本次测量范围。
